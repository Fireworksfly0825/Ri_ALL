# 9.14 日志 —— Pi 4B ↔ DJI M3E E-Port USB 链路排查

- 日期：2026-09-14
- 设备：树莓派 4B（Raspberry Pi OS，内核 6.1.21-v8+）
- 控制器：dwc2 @ `fe980000.usb`（USB-C 口，OTG / device 模式）
- 目标：让 E-Port 的 **USB bulk 链路**通了，PSDK payload 能在 Pi 上跑起来
- 一句话结论：**链路不通。** 电通了、控制器工作正常、主机也一直在反复尝试，
  但枚举从未成功过任何一步 —— 设备地址恒为 0、ep0 零收包，链路稳定卡在
  full-speed 之前。头号假设是"差分对信号质量劣化 → HS chirp 失败"。

> ⚠️ 本文只记录**接线状态下**的观测。
> 写这份日志时 Pi 处于"只通电开机、不接任何东西"的状态，
> 该状态下的数据没有诊断意义，故不收录。

---

## 1. 硬件拓扑

```
无人机 M3E
  └─ E-Port（12V 供电 + USB host + UART）
       │
       ├── 线B ──┐
       │         │
       │   [E-Port 转接板]  ← 降压（约 12V→5V）+ 引出 USB 与 UART
       │         │
       ├── 线A（Type-C to Type-C，跟 E-Port 一起配的原配线）──> Pi 4B 的 USB-C 口
       │                                                        ↑ 既是数据口，也是 Pi 的唯一供电口
       │
       └── CH340 USB-TTL 模块（插在 Pi 的 USB-A 口）──> E-Port 的 UART 引脚
                                                        （DUML 协议，921600）
```

要点：

- **Pi 的电就是这条 USB-C 链路来的**（E-Port → 转接板 → 线A → Pi USB-C）。
  这正是 E-Port 的标准 payload 架构：无人机既是 host 又供电。
  所以"电通"**不能**证明数据线没问题；反过来"数据不通"也不能靠万用表量出来。
- UART 链路（CH340）和 USB 链路是**两条独立的物理路径**，可以分别验证。
- 转接板本身是嫌疑面的一部分：线不止一根，还包含板上的 USB 座 / 走线 / 可能的 hub。

## 2. 判据：怎么才算"通了"（最重要的一条）

**唯一可靠判据是 dmesg 里出现：**

```
dwc2 fe980000.usb: new address N
```

（意思是主机的 SET_ADDRESS 被成功应答，枚举真正往前走了一步。）

⚠️ **只看 `new device is full-speed / high-speed` 会误判** ——
那只是每次 reset 都刷的"枚举开始"事件，**链路不通时会以约 1 次/秒无限刷下去**。
本次排查中途就因为把它当成"主机在正常工作"而误判过一次。

参考：**2026-09-13 19:40:43 唯一一次成功**的逐行日志

```
[14.518741] dwc2 fe980000.usb: bound driver configfs-gadget.pi4
[14.692071] dwc2 fe980000.usb: new device is high-speed
[14.828801] dwc2 fe980000.usb: new device is high-speed
[14.918299] dwc2 fe980000.usb: new address 1     ← 绑定后 0.4 秒内完成，之后事件停止
```

失败时长这样：只有 `new device is full-speed` 刷屏、**永远没有 new address**。

## 3. 现象（接线状态下的现场观测）

| 观测项 | 结果 |
|---|---|
| Pi 供电 | 正常。`vcgencmd get_throttled = 0x0`（无欠压、无降频），Pi 全程稳定运行 |
| 主机行为 | dmesg 持续刷 `new device is full-speed`，**1~2 次/秒**，开机后 10.3 秒就开始，连续 23 分钟（仅 t≈104s 有 39.5 秒空档） |
| 控制器实际速度 | `current_speed = full-speed`（能力上限 `maximum_speed = high-speed`） |
| 设备地址 | `DCFG` DEVADDR 始终为 **0** —— 主机从未给 Pi 分配过地址 |
| ep0 收包 | `DOEPINT(0) = 0` —— ep0 **从未收到过任何一个包**（连 SETUP 都没有） |
| SOF 帧号 | 30 秒连续采样**纹丝不动**冻在 1809；长期看只在极偶发窗口缓慢增长：896 → 1540 → 1809（跨约 20 分钟，**≈0.8 帧/秒**），远低于全速应有的 1000 帧/秒 |
| 动线测试 | 轻推 / 重压 线A 两端 + 动线B：SOFFN 只在 **2887~2889** 之间微动，**从未出现 high-speed，从未出现非 0 地址** —— 等于什么都没发生 |
| 无人机整机断电重上电 | 无效，通道依旧不通 |

**关键补充（用户确认）**：Pi 在动线过程中**掉过一次电**，且**不是主动断电**。
→ 说明供电接触在机械扰动下会断。这条给"接头/线材机械稳定性不足"加分。
→ 但要注意区分：断电后 Pi 立即恢复供电并正常启动，而**数据链路在通电状态下也一直不通**。
  所以"接触问题"目前只能解释掉电那一下，还解释不了数据不通。

## 4. 已确定的事实（一手证据）

| # | 事实 | 证据 |
|---|---|---|
| 1 | Pi 由这条 USB-C 链路供电，供电质量正常 | `throttled=0x0`；`GOTGCTL` bit19 BSESVLD=1；Pi 稳定运行 |
| 2 | dwc2 控制器工作在 **device（外设）** 模式 | `GOTGCTL` bit16 CONIDSTS=1；dr_mode=otg；GINTSTS bit0 CURMOD=0 |
| 3 | 控制器能力上限 **high-speed**，实际只协商到 **full-speed** | `maximum_speed`=high-speed / `current_speed`=full-speed；`DSTS` ENUMSPD=1 |
| 4 | 主机**从未**给 Pi 分配过设备地址 | `DCFG` = 0x00040000 → DEVADDR = 0（多次采样不变） |
| 5 | ep0 **从未**收到过任何一个包 | `DOEPINT(0)` = 0x00000000 |
| 6 | 主机能看到 Pi 的连接（D+ 上拉），并反复尝试 | `new device is full-speed` 持续刷屏 |
| 7 | 设备**收不到有效 SOF 流** | SOFFN 30 秒冻在 1809；长期平均 ≈0.8 帧/秒（应为 1000） |
| 8 | 供电导体（VBUS/GND）在整条链路上是通的 | 电要穿过 线B → 转接板 → 线A 才能点亮 Pi |
| 9 | 转接板 / 线B / E-Port 座的**机械配合**曾经是好的 | UART 走 线B + E-Port 座 + CH340，921600 稳定，抓到过 534 字节合法 DUML |
| 10 | 这条链路**能**跑 high-speed（不是 FS-only 的硬件） | 9-13 那次成功日志：两条 `new device is high-speed` + `new address 1` |
| 11 | 链路长期处于**边缘状态**，不是"昨天好今天坏" | kern.log 全量词频：`new device is full-speed` **6324** 次、`high-speed` **2** 次、`new address` **1** 次、`bound driver configfs-gadget.pi4` **24** 次 ⇒ **24 次开机里只成功过 1 次** |

**寄存器原始读数（接线状态下采集，多次采样稳定）**

```
GOTGCTL      = 0x000d0000     bit19 BSESVLD=1（VBUS 有效）、bit16 CONIDSTS=1（B-device）；ASESVLD=1
GINTSTS      = 0x0400802a     低 8 位含 bit3（SOF 中断）与 bit1
DSTS         = 0x00038002     SOFFN=0x380=896、ENUMSPD=1(full-speed)、SUSPSTS=0
               0x00060402     （另一次采样）SOFFN=0x604=1540
DCFG         = 0x00040000     DEVADDR = 0；DEVSPD 位域 = 0（控制器按 HS 配置）
DOEPCTL(0)   = 0x80008000     bit31 EPENA=1（ep0 OUT 已武装，在等主机发包）
DOEPINT(0)   = 0x00000000     从未收包
DIEPINT(0)   = 0x00000080     TXFE，良性
GNPTXSTS     = 0x00080020
```

⚠️ `UDC state` 恒为 `not attached` 是 udc-core / dwc2 的**显示假象**，不是"没 VBUS"
（`BSESVLD=1` 已否证）。本内核的 `dwc2.ko` **无任何模块参数**（没有
`force_b_session_valid` 这类开关可调）。

## 5. 已经排除的可能

- ❌ **不是充电线 / 缺 D+/D- 的线**：那种线连 ENUMDONE 都不会出现。
- ❌ **不是"整根线断开"**：断线不会产生 `new device` 记录，也不会让主机持续重试。
- ❌ **不是欠压 / 供电不足**：`throttled=0x0`。
- ❌ **不是"无人机 host 卡在坏状态里"**：无人机整机断电重上电后依旧不通 → 不是瞬时锁死，是稳定复现。
- ❌ **不是 Pi 侧"没插上"**：`new device` 持续刷屏说明主机看得到连接。
- ❌ **不是 dmesg 刷屏停了**：那是环形缓冲区满导致的假象（见踩坑 #6）。
- ❌ **不是 USB-C 插头方向问题**：翻面不可能有影响（见踩坑 #1）。

**仍未排除（按嫌疑排序）：**

1. ⚠️ **线 A**（原配 C-to-C，质量未知，反复插拔过）
2. ⚠️ **转接板上的 USB 座 / 走线 / 器件**（若板上 USB 经过 hub 或 ESD 器件）
3. ⚠️ **Pi 自己的 USB-C 口**（接触 + 焊接）
4. ⚠️ **无人机 E-Port 的 USB host 侧**

## 6. 头号假设：一个故障解释全部现象

> **差分对的交流特性劣化 → HS chirp 失败 → 降到 full-speed
> → 而嵌入式 host（无人机 E-Port）很可能只做 HS 枚举
> → 主机永远完不成枚举，只会不停 reset 重试。**

对照全部现象：

| 现象 | 解释 |
|---|---|
| VBUS 有效、`throttled=0x0`、Pi 跑得好 | 电源路径是好的（VBUS/GND 各 4 触点并联，只需直流导通） |
| `new device is full-speed` 持续刷屏 | 主机看得到 D+ 上拉、在反复 reset 重试 |
| max=high-speed / 实际=full-speed | HS chirp 握手失败（chirp K 是发在 **D-** 上的） |
| DEVADDR 恒为 0 | 枚举从没开始过 |
| DOEPINT(0) = 0 | ep0 一个包都没收到 |
| SOFFN ≈0.8 帧/秒 | 不是正常 SOF 流（应 1000/秒），只是复位尝试留下的残余 |
| 9-13 那次一切正常 | 那天 HS chirp 成了 → 主机立刻完成枚举（0.4 秒） |

**为什么不是"接触不良"这个词**：接触不良的典型表现是通断跳变、掉线、suspend 事件；
而这里是**稳定地劣化**（从无 suspend、刷屏节奏均匀）。⇒
更准确的描述是**虚接 / 半断 / 严重氧化 / 压接不良**这一类"直流还沾着、差分传不动"的状态。

**为什么"能供电"不是反例**：VBUS/GND 与 D+/D- 是分开的导体。
供电是直流特性（各 4 触点并联、PMIC 容差 ±5%），数据是一对差分线扛
480 Mbps 微秒级握手 + 16 位 CRC。而且约 1A 的 payload 电流要经同一个连接器的
GND 回流，接触电阻造成的 IR drop / 地弹足以打死 HS chirp，而 `get_throttled`
仍然显示 0x0。**"电通、数据不通"正是这类劣化的标准签名，万用表量不出来。**

## 7. 踩过的坑 / 被推翻的判断（避免重复走）

| # | 曾经的判断 | 为什么错 | 教训 |
|---|---|---|---|
| 1 | "翻一下 USB-C 插头方向试试" | USB-C receptacle 的 A6/A7 与 B6/B7 是**并联**的，翻面就是靠这个实现的 | 别浪费时间翻面 |
| 2 | "`new device is full-speed` 刷屏 = 主机在正常工作" | 那只是枚举开始事件，失败时 1 次/秒无限刷 | **只认 `new address`** |
| 3 | "SOFFN 两次采样不同（1540 / 896）⇒ 收到 SOF、总线是活的" | 30 秒连续采样冻在 1809 不动；长期只有 ≈0.8 帧/秒 | 计数器"有变化"≠"正常"，**要算速率** |
| 4 | "D- 那根导体断了" | D+ 上拉可见、reset 能被察觉、9-13 还成功跑过 HS ⇒ 不是整根断 | 是"虚接/半断/氧化"，不是断 |
| 5 | "线 A 可能是随手拿的充电线" | 线 A 是跟 E-Port 一起配的原配线 | 但原配线也会坏，尤其反复插拔过 |
| 6 | 想用万用表量通断来判断 | 现在直流是通的，量出来一定"正常"。要找的是**交流特性**劣化 | 万用表在这类故障上没有分辨力 |
| 7 | "dmesg 刷屏停了（`grep -c` 计数卡在 2337 不动）" | dmesg 是**环形缓冲区**，早期记录被挤掉了；计数饱和≠事件停止 | 判断"是否还在刷"要看**时间戳差**，不要看累计计数 |
| 8 | —— | **Pi 重启会清空 dmesg**，重启前的证据只剩本记录 | **先落盘，再重启/再拔线** |

## 8. 卡住的问题

1. **主机到底有没有发 SETUP？** `DOEPINT(0)=0` 有两种解释，无法从 Pi 端区分：
   - (A) 主机发了，但传输质量太差，Pi 收不到 / 解不出 → 问题在物理层
   - (B) 主机压根没发，自己卡在 "reset → 超时 → 再 reset" 的循环里 → 线可能完全没问题
2. **"主机只认 high-speed"这个假设无法验证** —— 除非让链路真正跑起来一次，或用 USB 协议分析仪看。
3. **故障点无法定位到具体某根线 / 某个接头**。证据只能把范围收敛到
   「Pi USB-C 口 ∪ 线A ∪ 转接板 USB 座/走线 ∪ 无人机 host 侧」。
4. **动线那一秒掉的电**：能证明某个接头机械稳定性不足，但无法指认是哪一个
   （Pi 端 / 转接板端 / 线A 本体 / 线B）。

## 9. 下一步计划（按性价比排序）

> 前提：先把拓扑恢复成"无人机上电 + 线A + 线B + 转接板 + CH340 全接上"。
> 当前"只给 Pi 通电、什么都不接"的状态下不要做任何测量。

**第 0 步：恢复实验条件**
- [ ] CH340 插回 Pi 的 USB-A，确认 `ls /dev/ttyUSB0` 出现（先证明 UART 通路还在）
- [ ] 无人机上电，确认 E-Port 正常输出
- [ ] 全程尽量不动线，避免再触发掉电

**第 1 步：冷启动采集（零成本，先拿到干净的一手数据）**

因为重启会清 dmesg，**先把采集落盘**：

```bash
cat > ~/usb_log.sh <<'EOF'
#!/bin/bash
D=/sys/kernel/debug/usb/fe980000.usb
U=/sys/class/udc/fe980000.usb
OUT=~/usb_log_$(date +%m%d_%H%M%S).txt
{
  echo "=== 启动: $(uptime -s)  现在: $(date +%T)  供电: $(vcgencmd get_throttled) ==="
  for i in $(seq 1 60); do
    printf "%s  " "$(date +%T.%2N)"
    sudo cat $D/regdump | grep -E "^(DSTS|DCFG|GINTSTS|GOTGCTL|DOEPINT\(0\)|DOEPCTL\(0\))" | tr '\n' ' '
    echo "  state=$(cat $U/state) speed=$(cat $U/current_speed)"
    sleep 1
  done
  echo "=== dmesg ==="; dmesg | grep -iE "dwc2|usb|gadget|ffs"
} > "$OUT" 2>&1
echo "已保存: $OUT"
EOF
chmod +x ~/usb_log.sh
```

流程：**无人机断电 → 跑 `~/usb_log.sh` → 无人机上电 → 等 60 秒 → 看文件**。
只看三件事：dmesg 里有没有 **`new address`**、`current_speed` 有没有变成 high-speed、
DEVADDR 有没有变成非 0。

**第 2 步：接头扰动测试（判断"接触" vs "通路本体"）**

```bash
sudo python3 ~/soffn_watch.py
```

脚本自己会判断并打印结论（★ 行标记第几秒出现变化），你只管推接头：
- 推 **Pi 的 USB-C 口**、推 **转接板的 Type-C 座**（两端都推，别拔）
- SOFFN 开始飞涨 或 出现 high-speed ⇒ 接触问题，部位 = 你刚动的那个接头
- 全程无变化 ⇒ 推压力度没用，问题在通路本体 → 换线 A

> 上一轮结果：SOFFN 只在 2887~2889 微动，什么都没发生；
> 而且那一轮把 Pi 弄掉电了，环境被破坏，**这一轮需要重做**（这次先看住供电）。

**第 3 步：换线 A**
用一根**你确定传过数据**的 C-to-C（笔记本 / 硬盘盒配的），重跑第 1 步对比。
这是最便宜、最可能一步排除的环节。

**第 4 步：Pi ↔ PC 对照测试（决定性，但需本地终端！）**

把 Pi 的 USB-C 通过线 A 接到 PC：
- PC 认到 **high-speed** ⇒ Pi + 线 A 清白，问题在无人机 / 转接板一侧
- PC 也只认到 full-speed 或认不到 ⇒ 问题在 **Pi 的 USB-C 口 或 线 A**

> ⚠️ **前提**：Pi 的电就是这根线来的，一拔就断电，Remote-SSH 会立刻掉。
> 做这个测试前必须先有本地终端（Pi 上已插着 Logitech K120 键盘，加 HDMI 即可）。

**第 5 步：若前四步都没结果**
把嫌疑推向转接板（USB 座 / 走线 / 板上的 hub 或 ESD 器件）与无人机 E-Port 的 host 侧；
此时值得上的手段是 USB 协议分析仪，或换一块已知良好的转接板做替换法。

## 10. 附录：关键命令速查

```bash
# 寄存器（比 dmesg 硬一层）
sudo cat /sys/kernel/debug/usb/fe980000.usb/regdump
sudo watch -n0.2 'grep ^DSTS /sys/kernel/debug/usb/fe980000.usb/regdump'   # 16 进制冻住 = 收不到 SOF

# UDC 状态
cat /sys/class/udc/fe980000.usb/state          # 注意：恒为 not attached 是显示假象
cat /sys/class/udc/fe980000.usb/current_speed  # full-speed / high-speed
cat /sys/class/udc/fe980000.usb/maximum_speed

# 判断"刷屏是否还在继续"（不要用 grep -c！）
a=$(dmesg | tail -1); sleep 10; echo "$a"; dmesg | tail -1

# 查历史日志（kern.log 含 NUL 字节，必须加 -a）
grep -a "new address" /var/log/kern.log

# 供电
vcgencmd get_throttled     # 0x0 = 正常
```

**寄存器解码速查（dwc2）**

| 寄存器 | 位域 | 含义 | 本次读数 |
|---|---|---|---|
| GOTGCTL | bit19 BSESVLD | B-session 有效（= VBUS 有电） | 1 ✅ |
| GOTGCTL | bit16 CONIDSTS | 1 = B-device（外设模式） | 1 ✅ |
| GINTSTS | bit3 SOF | 收到 SOF 中断 | 1 |
| GINTSTS | bit0 CURMOD | 0 = device 模式 | 0 ✅ |
| DSTS | ENUMSPD | 0=HS 1=FS 2=LS | 1 = full-speed ⚠️ |
| DSTS | SOFFN | SOF 帧号，全速正常应 ~1000/秒 | 896 → 1540 → 1809 → 2887（≈0.8/秒）❌ |
| DCFG | DEVADDR | 主机分配的设备地址 | 0 = 从未枚举 ❌ |
| DOEPCTL(0) | bit31 EPENA | ep0 OUT 已武装 | 1 ✅ |
| DOEPINT(0) | — | ep0 收包中断 | 0 = 一个包都没收到 ❌ |

**其他资源**
