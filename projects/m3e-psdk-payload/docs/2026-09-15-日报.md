### 2. 降落卡死根因定位（今天最重要的结论）

**现象**：日志停在 `Now flight is in auto landing mode.` 之后再也没有 `Successful landing` / `Step 4: Release joystick authority` / `sample end`。

两次测试的完成度判据（**这是判断"跑通没有"的硬指标**）：

| 日志文件 | Successful take off | Successful landing | Release joystick | sample end |
|---|---|---|---|---|
| `DJI_0002_20260915_16-31-13.log` | 1 | **0** | **0** | **0** |
| `DJI_0003_20260915_16-58-20.log` | 1 | **0** | **0** | **0** |

**根因**：**M3E 的自动降落不会直接触地，它先降到 0.45~0.55m 悬停，等 app 调 `DjiFlightController_StartConfirmLanding()` 才继续落下去。** 而子菜单 1/2/4 走的 `DjiTest_FlightControlMonitoredLanding()`（调用点 `test_flight_control.c:380` 和 `:449`）**只调 `StartLanding()`，然后死等，永远不调 confirm** → 必然死锁。

对比：子菜单 3 走的 `DjiTest_FlightControlGoHomeAndConfirmLanding()` 就处理对了（`test_flight_control.c`）：

```c
2272:    USER_LOG_INFO("Start landing action");
2275:    while (GetValueOfDisplayMode() == DISPLAY_MODE_AUTO_LANDING &&
2276:           GetValueOfFlightStatus() == FLIGHT_STATUS_IN_AIR) {
2279:        T_DjiFcSubscriptionHeightFusion heightFusion = DjiTest_FlightControlGetValueOfHeightFusion();
2280:        s_osalHandler->TaskSleepMs(1000);
         /* M3E / M3T / M3D ... 机型分支： */
2291:        if ((dji_f64_t) 0.45 < heightFusion && heightFusion < (dji_f64_t) 0.55) {
2292:            break;              // ← 悬停到 0.5m 就跳出
2293:        }
         /* 其它机型是 0.65 ~ 0.75 */
2304:    djiStat = DjiFlightController_StartConfirmLanding();   // ← 补上这一步才能落地
```

而且 `DjiTest_FlightControlLandFinishedCheck()`（`test_flight_control.c:2142`）是个**没有超时上限的死循环**，所以卡住之后永远不会自己退出：

```c
bool DjiTest_FlightControlLandFinishedCheck(void)
{
    while (GetValueOfDisplayMode() == DISPLAY_MODE_AUTO_LANDING ||
           GetValueOfFlightStatus() == FLIGHT_STATUS_IN_AIR) {
        s_osalHandler->TaskSleepMs(1000);       // 无超时，无退出条件
    }
    ...
}
```

**用户侧验证**：在遥控器上手动确认降落后，高度回到 0.00m —— 与上述诊断完全吻合，是根因确认。

**结论**：这是 **DJI 样本的缺陷，不是我们接线 / RC / 配置的问题**。要演示完整的"起飞→飞行→降落"闭环，应使用**子菜单 3**（take off go home force landing），它走的是带 confirm 的那条路径。

### 3. PSDK 开机自启动（已修好）

**原来为什么起不来 —— 三层原因叠加**：

1. **`/etc/rc.local`** 开头是 `#!/bin/sh -e`，第 46 行 `cd ${PSDK_TOP_DIR}` 展开成 `cd XXX`（`/etc/environment` 里是出厂占位符 `XXX`/`YYY`），失败即中止整个脚本 → 第 48 行 `sudo YYY` 从来没执行过。`rc-local.service` 因此长期 `failed`：

   ```
   ● rc-local.service - /etc/rc.local Compatibility
        Active: failed (Result: exit-code) since Tue 2026-09-15 15:54:27 CST
        Process: 637 ExecStart=/etc/rc.local start (code=exited, status=2)
   ```
   `status=2` 正是 `cd XXX` 失败退出码。

2. **`psdk.service`** 存在但是 **disabled**，且它调用的 DJI `psdk-alive.sh` 期望的是
   `/home/ws/payload-sdk/build/{b-AMA1,u-AMA2}/dji_sdk_demo_linux` 那套**双载荷 Linux 生产部署**，
   而 `/home/ws` 从未挂载（`/etc/fstab` 里 `/dev/mmcblk0p3` 那行被注释）。直接 enable 只会 `invailed root dir` 退出。

3. **隐藏危害**：rc.local 那段用 `sudo` 跑，`sudo rm ./Logs -rf` + root 身份启动会把 `build/bin/Logs/` 属主改成 root，
   而 PSDK 以 rsp 启动时遇到 root 属主的 Logs 会直接 `file system init error` 退出 ——
   **这就是历史上那个"Logs 属主"坑的源头**。

**修法 —— 没有去修 DJI 那套不适用的机制，而是新建了一套贴合实际布局的**：

| 位置 | 作用 |
|---|---|
| `/etc/systemd/system/psdk.service` | 新单元，**故意放 /etc 覆盖** `/usr/lib` 里 DJI 同名单元（DJI 原文件保持不动） |
| `/home/rsp/dji/psdk/start/psdk-run.sh` | 看门狗：等串口 → 在 screen 会话里跑 demo → 死了自动拉起（指数退避，上限 300s） |
| `/home/rsp/dji/psdk/start/psdk-stop.sh` | ExecStop 清理 screen 会话 |
| `/etc/environment` | `XXX`/`YYY` → 真实路径 |
| `/etc/rc.local` | 删掉整段 PSDK 逻辑（保留 raspigadget / vsftpd / adb） |

**关键设计：全程以 user `rsp` 运行，不是 root** —— 从根上杜绝再制造 root 属主的 `Logs/`。

**为什么用 `screen` 而不是 `/dev/null`**：demo 顶层的 `std::cin >> inputChar`（`main.cpp:81`）如果读到 EOF **不会阻塞在菜单上**。
实测确认（`g++ -std=c++11`，哨兵 `char c=0xAB`）：
```
--- stdin 来自 /dev/null ---      eof=1 fail=1 value=171   ← 哨兵原样保留，并未清零
--- 管道给一个字符 '1' 后 EOF ---  eof=0 fail=0 value=49
```
即 libstdc++ **不按 C++11 "value zero is stored" 把 char 清零**，`switch(inputChar)` 会拿**未初始化的栈垃圾**去匹配，理论上能命中任意 case。
用 pty（screen 会话）让读操作一直阻塞就绕开了这个风险。

**服务实测日志**（`journalctl -u psdk.service`）：

**开机路径风险已逐条排查（未重启验证）**：

### 4. 顺带修掉的两个隐患（会让"常驻"变成灾难）

服务跑起来后才暴露 —— **手动跑几分钟完全看不出来**：

**(1) `media_file/out.h264` 属主是 root，导致相机模拟器空转**

相机模拟器是按**读写**打开的（`test_payload_cam_emu_media.c:1321`）：
```c
fpFile = fopen(transcodedFilePath, "rb+");
```
该文件一度是 `root:root 644`，rsp 读得了写不了 → `errno 13`（EACCES）→ 掉进 `send:` 标签后面**没有 sleep 的裸 `continue` 紧循环**：
```c
   send:
       if (fpFile == NULL) {
           USER_LOG_ERROR("open video file fail.");
           continue;                        // ← 无 sleep，纯自旋
       }
```
实测刷屏 **190 KB/s**，CPU 烧到 **20~33%**。
修法：`sudo chown rsp:rsp media_file/out.h264`。
⚠️ 注意：改完属主**必须重启进程**才生效，老进程会一直沿用失败状态（我中途就被这个误导过一次）。

**(2) 落盘日志级别默认 DEBUG，会写 10 GB/天**

`application.cpp:138` 原本写死：
```c
localRecordConsole.consoleLevel = DJI_LOGGER_CONSOLE_LOG_LEVEL_DEBUG;
```
把每条 DUML 链路报文和遥测原始帧都写进 `build/bin/Logs/DJI_*.log`，实测约 **124 KB/s ≈ 10 GB/天**。
磁盘当前 11G/29G（剩 18G），**按这个速率不到两天就写满**。

已改成**环境变量控制、默认 INFO**：
```c
const char *fileLogLevel = getenv("PSDK_FILE_LOG_LEVEL");
if (fileLogLevel != NULL && strcasecmp(fileLogLevel, "DEBUG") == 0) {
    localRecordConsole.consoleLevel = DJI_LOGGER_CONSOLE_LOG_LEVEL_DEBUG;
} else {
    localRecordConsole.consoleLevel = DJI_LOGGER_CONSOLE_LOG_LEVEL_INFO;
}
```
需要抓链路细节时 `PSDK_FILE_LOG_LEVEL=DEBUG` 起一次即可，不丢排障能力。
重编：`cd build && make dji_sdk_demo_on_rpi_cxx`（只重编 `application.cpp`，约 3 秒）。

**修复效果对照**：
